# MIMIHALL Daily Briefing(Rev.4) 뉴스 필터 점검 및 수정안

- 대상: n8n 워크플로우 `MIMIHALL Daily Briefing(Rev.4)` (매일 08:00 / 15:00 실행, 텔레그램 @mimihall5 전송)
- 증상: 하루에 걸러져 나오는 뉴스가 너무 적어 볼 것이 없음
- 결론: **필터가 4단계로 겹쳐 있고, 각 단계가 독립적으로 "절대 기준"으로 컷을 하기 때문에 과도하게 걸러지는 구조가 맞습니다.** 특히 `Gemini 중요도 80점 이상` + `키워드당 1건`이 결합된 부분이 핵심 원인입니다.

> 확인 범위에 대한 주의: 이 세션의 컨테이너에서는 `n8n.ybee.cloud`, `portal.ybee.cloud` 접근이 프록시 정책으로 차단(403)되어 실제 워크플로우 노드 설정을 직접 열어보지는 못했습니다. 아래 내용은 `ObsidianVault/session_logs`에 기록된 파이프라인 설계(2026-01-29 진단, 2026-02-19 n8ndb 연동 기록)를 근거로 한 것입니다. n8n 화면에서 각 노드의 실제 값을 확인하며 적용해 주세요.

## 1. 현재 파이프라인 (기록 기준)

| 단계 | 노드/처리 | 현재 기준 | 성격 |
|---|---|---|---|
| ① 수집 | Google News RSS (키워드별) | 키워드 22개 | 입력 |
| ② 중복 제거 | OLLAMA `nomic-embed-text` 임베딩 + 코사인 유사도 | **0.85 이상이면 중복 처리** | 컷 |
| ③ 중요도 판정 | Gemini Flash 채점 (`ai_importance`, `ai_reason`) | **80점 이상만 통과** | 컷 |
| ④ 대표 선정 | 키워드당 최고점 1건만 저장/전송 | **키워드당 1건** | 컷 |
| ⑤ 전송/저장 | `n8ndb.daily_briefings` 저장 → 텔레그램 @mimihall5 | 하루 2회 | 출력 |

리포트 생성기(`report_generator.py`)는 여기서 저장된 것 중 최근 20건을 읽어 다시 Gemini로 80점 이상 상위 5건을 고릅니다. 즉 같은 80점 기준이 **두 번** 적용됩니다.

## 2. 왜 과도하게 걸러지는가

### 2-1. 산술적 상한이 매우 낮음
- 키워드 22개 × 하루 2회 × 키워드당 1건 = **이론상 최대 44건/일**.
- 여기에 "80점 이상" 조건이 붙으므로, 특별한 뉴스가 없는 종목은 그 회차에 **0건**이 됩니다.
- 실제로는 하루 5~15건 수준으로 떨어질 가능성이 높고, 조용한 날은 한 자릿수가 됩니다. 사용자가 느끸 "볼 게 없다"는 이 구조의 자연스러운 결과입니다.

### 2-2. LLM 채점을 절대 임계값(80점)으로 사용
- Gemini Flash류 모델의 0~100 채점은 **분포가 보수적**입니다. 루브릭 없이 물으면 대부분 50~75점대에 몰리고, 80점 이상은 "실적 발표, 대형 수주, 규제 결정" 같은 명백한 이벤트에만 나옵니다.
- 채점 프롬프트에 "80점 이상만 통과"라는 의도가 들어가면 모델이 더 보수적으로 채점하는 경향도 있습니다.
- 결과: 평소 장세에서는 컷을 넘는 기사가 거의 없어 필터가 사실상 "이벤트 감지기"처럼 동작합니다. 매일 브리핑 용도라면 기준이 너무 높습니다.

### 2-3. 키워드당 1건 고정
- 대형주(삼성전자, LG에너지솔루션 등)는 하루 수십 건 중 1건만 남고, 소형주는 애초에 기사가 없어 0건입니다. 결과적으로 **보여줄 게 많은 종목에서 가장 많이 버려집니다.**

### 2-4. 유사도 0.85 중복 제거는 과잉 병합 가능
- `nomic-embed-text` 기준 0.85는 "같은 사건을 다룬 다른 관점의 기사"까지 하나로 묶기 쉬운 값입니다. 같은 종목 뉴스는 문맥이 비슷해 유사도가 전반적으로 높게 나옵니다.
- 이 단계는 상대적으로 영향이 작지만, 후속 80점 컷에 들어가는 후보 수를 줄이는 요인입니다.

### 2-5. 컷이 "AND"로 겹침
- 각 단계가 걸러낸 뒤 다음 단계로 넘기는 구조라, 최종 통과율은 각 단계 통과율의 **곱**입니다. 어느 한 단계만 조금 완화해서는 체감이 크지 않고, ③과 ④를 함께 조정해야 합니다.

## 3. 실제 수치로 확인하는 방법 (n8ndb)

n8n 컨테이너 네트워크 안에서 `n8ndb`에 접속해 아래 쿼리를 실행하면 "얼마나 걸러지는지"를 정량적으로 볼 수 있습니다. (`psql -h n8n-postgres-1 -U evergreen -d n8ndb`)

```sql
-- (A) 최근 14일, 날짜별로 실제 전송된 건수
SELECT sent_date::date AS d, COUNT(*) AS sent
FROM daily_briefings
WHERE sent_date >= NOW() - INTERVAL '14 days'
GROUP BY 1 ORDER BY 1;

-- (B) 저장된 기사들의 ai_importance 분포 (80 컷 직전 값들이 어디에 몰리는지)
SELECT width_bucket(ai_importance, 0, 100, 10) AS bucket,
       MIN(ai_importance) AS lo, MAX(ai_importance) AS hi, COUNT(*) AS n
FROM daily_briefings
WHERE sent_date >= NOW() - INTERVAL '30 days'
GROUP BY 1 ORDER BY 1;

-- (C) 키워드별 채움률: 최근 14일 × 2회 = 28 슬롯 중 몇 번 뉴스가 나왔는가
SELECT keyword, COUNT(*) AS filled, ROUND(100.0*COUNT(*)/28, 1) AS fill_pct
FROM daily_briefings
WHERE sent_date >= NOW() - INTERVAL '14 days'
GROUP BY keyword ORDER BY filled DESC;
```

해석 기준:
- (A)가 하루 10건 미만이면 과잉 필터 확정.
- (B)에서 80~89 구간에 몰려 있고 90 이상이 거의 없으면, 모델이 "80을 겨우 넘긴" 기사만 통과시키는 상태입니다. 70~79 구간이 비어 있는 것은 저장 자체가 안 됐기 때문이며, **탈락 기사는 로그가 없어 복구 불가**합니다(4-5 참고).
- (C)에서 채움률 30% 미만 키워드가 절반 이상이면 ③ 기준이 너무 높습니다.

n8n 화면에서도 확인 가능합니다: 워크플로우 실행 내역(Executions)에서 Gemini 채점 노드의 출력 아이템 수와 그 다음 IF/Filter 노드의 통과 아이템 수를 비교하면 회차별 탈락률이 바로 보입니다.

## 4. 수정안 (권장 순서대로)

### 4-1. [핵심] 절대 컷 → 상대 순위 + 완화된 하한
- 채점은 그대로 두고, **필터 조건을 `>= 80` 에서 `>= 60` 으로 내리고**, 키워드당 **상위 3건**을 남기도록 변경합니다.
- 60점 미만이어도 해당 키워드에 통과 기사가 하나도 없으면 **최고점 1건은 "참고" 태그로 통과**시킵니다(브리핑이 비는 것을 막는 fallback).
- 텔레그램 메시지에서는 `ai_importance` 값을 함께 표기해 사용자가 중요도를 스스로 판단할 수 있게 합니다(예: `[85]`, `[62]`).

기존 IF 노드 대신 Code 노드 하나로 처리하는 예시입니다(입력: 채점이 끝난 기사 아이템들, 필드명은 실제 노드 출력에 맞춰 수정):

```javascript
// n8n Code 노드 (Run Once for All Items)
const MIN_SCORE   = 60;  // 기존 80
const TOP_N       = 3;   // 기존 1
const FALLBACK_MIN = 45; // 통과 기사가 없을 때 참고용으로 보낼 최저점

const byKeyword = {};
for (const item of $input.all()) {
  const k = item.json.keyword;
  (byKeyword[k] ??= []).push(item.json);
}

const out = [];
for (const [keyword, articles] of Object.entries(byKeyword)) {
  articles.sort((a, b) => (b.ai_importance ?? 0) - (a.ai_importance ?? 0));
  let picked = articles.filter(a => (a.ai_importance ?? 0) >= MIN_SCORE).slice(0, TOP_N);
  if (picked.length === 0 && articles.length > 0 && (articles[0].ai_importance ?? 0) >= FALLBACK_MIN) {
    picked = [{ ...articles[0], is_fallback: true }];
  }
  for (const a of picked) out.push({ json: { ...a, keyword } });
}
return out;
```

### 4-2. Gemini 채점 프롬프트에 루브릭 고정
채점 기준을 명시하면 점수 분포가 안정되어 임계값 튜닝이 쉬워집니다. 프롬프트에 다음 문구를 추가하세요.

```
점수 기준(0~100):
90~100: 실적 발표, 대규모 수주/계약, M&A, 규제·정책 확정, 유상증자 등 주가에 직접 영향
70~89 : 신제품/기술 발표, 경쟁사 동향, 산업 정책 논의, 애널리스트 목표가 변경
50~69 : 업황 관련 일반 뉴스, 인터뷰, 컨퍼런스 참가, 단순 시황 언급
0~49  : 단순 언급, 광고성, 종목과 무관
같은 사건을 다룬 기사라도 새로운 정보가 있으면 감점하지 마세요.
```
"80점 이상만 선별하라"처럼 필터 의도를 프롬프트에 넣지 마세요. 채점과 필터를 분리해야 임계값을 바꿀 때 재채점이 필요 없습니다.

### 4-3. 중복 제거 임계값 완화
- 코사인 유사도 **0.85 → 0.92**로 올려, 거의 같은 기사(전재/제목만 다른 기사)만 중복으로 묶도록 합니다.
- 중복으로 묶인 기사는 버리지 말고 대표 기사에 `related_count`로 붙여 두면 "얼마나 많이 다뤄진 사건인지"가 보여 중요도 판단에 도움이 됩니다.

### 4-4. 리포트 쪽 2차 필터와 기준 맞추기
- `report_generator.py`의 "상위 5건 (80점+)"도 같은 값(60점, 상위 5건)으로 맞추세요. 브리핑 저장 기준을 내렸는데 리포트가 다시 80점으로 자르면 리포트에는 여전히 뉴스가 비게 됩니다.

### 4-5. 탈락 기사 로깅 (튜닝용)
- 현재는 컷을 넘은 기사만 `daily_briefings`에 저장되어, 임계값이 적절한지 사후 검증이 불가능합니다.
- 채점 직후 모든 기사를 `daily_briefings_scored`(또는 기존 테이블에 `is_sent boolean` 컬럼 추가)로 저장하고, 전송 여부만 플래그로 구분하세요. 1~2주 데이터가 쌓이면 3장의 (B) 쿼리로 실제 분포를 보고 임계값을 데이터 기반으로 다시 정할 수 있습니다.

## 5. 적용 후 기대치와 검증

| 항목 | 현재(추정) | 변경 후(기대) |
|---|---|---|
| 하루 전송 상한 | 44건 | 132건 (22×2×3) |
| 조용한 날 실제 전송 | 0~10건 | 20~40건 (fallback 포함, 키워드마다 최소 1건 근접) |
| 활발한 날 실제 전송 | 15~25건 | 50~80건 |

- 변경 후 1주일 동안 3장의 (A), (C) 쿼리를 매일 확인하세요. 하루 전송량이 **80건을 넘어 피로감**이 생기면 `MIN_SCORE`를 65~70으로, 여전히 적으면 `TOP_N`을 4~5로 조정합니다.
- 텔레그램 메시지가 길어질 수 있으므로 회차당 30건을 넘으면 점수순으로 2~3개 메시지로 분할해 전송하도록 Split 노드를 추가하는 것을 권장합니다.

## 6. 요약

- 과도한 필터링이 맞습니다. 원인은 `Gemini 80점 절대 컷` × `키워드당 1건` × `유사도 0.85 중복 병합`이 AND로 겹치는 구조입니다.
- 가장 효과가 큰 한 가지 수정은 **80점 컷을 60점 + 키워드당 상위 3건 + fallback 1건**으로 바꾸는 것(4-1)입니다.
- 채점 프롬프트에서 필터 의도를 빼고 루브릭을 고정(4-2)하면 이후 튜닝이 쉬워지고, 탈락 기사 로깅(4-5)을 추가하면 다음 조정은 데이터로 결정할 수 있습니다.
